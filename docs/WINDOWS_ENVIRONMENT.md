# Reproducible Windows software environment

The initial qualified profile is Windows 11 x64, conda-forge CPython **3.11.15
h0159041_1_cpython**. `requirements/windows-cp311/profile.json` identifies its
interpreter binaries/support artifacts, exact runtime/build/development versions,
wheel filenames and SHA-256 values. This profile is software acceptance scope;
it does not certify laboratory apparatus or a particular experimental protocol.
Other interpreter distributions require separate qualification. Do not replace
global Python or a functioning installation to try this profile.

## Obtain the interpreter separately

The launcher does **not** install Python or invoke Conda. Python.org provides no
Windows installer for 3.11.15. The tested acquisition method uses an existing
Conda installation (qualification used 25.7.0) solely to provision the interpreter.
Conda is not an application runtime dependency or a universal policy for all future
profiles. A second laboratory must review its provisioning tool/installer and
licensing; a copied virtual environment is not a portable interpreter installer.

Use the 19 exact URLs and hashes in `interpreter-artifacts.json`, not an unpinned
`conda install python=3.11` resolution. For example, in PowerShell, from a reviewed
full PsyCoLab checkout, choose new locations outside existing laboratory roots:

```powershell
$artifactCache = 'C:\PsyCoLabSoftware\InterpreterArtifacts'
$interpreterPrefix = 'C:\PsyCoLabSoftware\Python31115'
New-Item -ItemType Directory -Force -Path $artifactCache | Out-Null
$artifacts = Get-Content -Raw requirements/windows-cp311/interpreter-artifacts.json | ConvertFrom-Json
$explicitLines = @('@EXPLICIT')
foreach ($artifact in $artifacts) {
    $target = Join-Path $artifactCache $artifact.filename
    if (-not (Test-Path -LiteralPath $target)) {
        Invoke-WebRequest -Uri $artifact.source -OutFile $target
    }
    if ((Get-FileHash -Algorithm SHA256 -LiteralPath $target).Hash.ToLowerInvariant() -ne $artifact.sha256) {
        throw "Interpreter artifact hash mismatch: $($artifact.filename)"
    }
    $explicitLines += ([System.Uri]$target).AbsoluteUri
}
$explicitFile = Join-Path $artifactCache 'interpreter-explicit.txt'
[IO.File]::WriteAllLines($explicitFile, $explicitLines, [Text.UTF8Encoding]::new($false))
conda create --offline --copy --no-default-packages --yes --prefix $interpreterPrefix --file $explicitFile
$env:PSYCOLAB_BOOTSTRAP_PYTHON = Join-Path $interpreterPrefix 'python.exe'
.\run_psycolab.bat
```

Do not overlay an existing interpreter prefix. Downloaded bytes must match SHA-256
before use; there is no fallback to different versions. See the qualification
report for the tested host and exact source. An independent second-workstation
rehearsal remains Stage 4, not an implication of these commands.

## First and repeat setup

Keep the existing `run_psycolab.bat` interface. A correctly identified local .venv
is preferred on repeat launch. For a fresh checkout, the optional
`PSYCOLAB_BOOTSTRAP_PYTHON` names one interpreter executable, not a shell command.
The setup script checks exact implementation, patch, x64, Python executable/DLL
hashes and required conda artifact identities before installation.

First setup creates an owned .venv, records an incomplete-attempt marker, installs
hash-pinned binary build/runtime wheels, and installs the checkout editably using
`--no-deps --no-build-isolation`. Pip installation reports are checked against
the reviewed wheel filenames/hashes. Source/version/editable identity, installed
versions/file integrity and `pip check` must pass before atomic successful state
is written. No scientific run record or extension Ready status is written by setup.

Unchanged repeat launch checks lock/profile identity, interpreter/support-binary
identity, installed core file hashes, full observed package inventory and editable
source identity. It does not reinstall dependencies or rewrite successful state.
Generated bytecode is excluded from integrity seals; path-containing installed
scripts are sealed per installation, not assumed byte-identical across computers.

If setup fails before successful state is written, the matching owned pending
attempt can retry the **same** reviewed profile. It uses the same exact hashes,
never an unrestricted upgrade. A changed profile/specification, pre-existing
unqualified environment, wrong interpreter, wrong version or changed package file
is preserved and refused with instructions to use a separate reviewed checkout.
No old environment is silently renamed/deleted. Only editable source metadata
may be refreshed in place after the core environment is verified; dependencies
remain fixed. A lost/corrupt pip or interrupted interpreter/venv creation may need
a new checkout rather than automatic repair. Arbitrary process-kill rollback is
not promised.

For offline qualification, `PSYCOLAB_WHEELHOUSE` may point to a directory containing
the exact reviewed wheels. Pip then uses `--no-index --find-links`; hashes and
binary-only enforcement still apply. This is pip's existing wheel-directory
facility, not a new downloader, service or #124 diagnostics system.

## USER_env and development

`run_user_env.bat` and `launcher_setup.py --user-env` retain the separate USER_env
workflow. Existing `user_requirements.txt` is never rewritten. Extras resolve
against `core.constraints`, with a dry run before installation; an incompatible
core/tool requirement is rejected. The observed augmented inventory is recorded,
but arbitrary lab extras are not represented as a fully hash-locked release.
Their owners must qualify them and retest affected studies. No Ready promotion
occurs, and missing unrelated optional libraries do not become global dependencies.

Keep pytest and its dependencies separate from ordinary installations.
`development.lock` is for a separate developer/test environment and CI; adding
packages manually to a qualified application .venv invalidates its recorded
inventory. A developer can use the approved interpreter to create a separate
venv, install build.lock and development.lock with `--require-hashes
--only-binary=:all:`, then install this checkout with `--no-deps
--no-build-isolation -e .`. Hosted CI uses those locks but may use a different
Windows Python distribution; it is source regression coverage, not exact-profile
installer qualification.

## Stage 4 first-time researcher checklist

- [ ] Record Windows 11 edition/build, approved interpreter artifact/build and
  source commit; provision a new prefix and checkout without touching an old lab.
- [ ] Verify interpreter and dependency artifacts, first launcher setup and
  `.venv/.psycolab-setup.json`; restart and confirm unchanged versions/profile.
- [ ] List all ten experiments; run a short synthetic experiment and validate
  its saved folder with `scripts/validate_run.py`.
- [ ] Check the intended external data/config/calibration roots; enable only a
  reviewed trusted extension and exercise Test then deliberate software Ready.
- [ ] Check source/preset editor handoff and generic Configure/Review with a human
  researcher; distinguish software Ready from physical qualification.
- [ ] Exercise documented setup refusal and retry routes; retain old working
  installations and never clear errors by deleting scientific source/records.

An independent Windows 11 workstation is required for Stage 4 sign-off.

## Stage 5 retained-installation preparation

Retain the old full checkout/environment and backups plus exact source/root and
environment identities. Prepare and validate the new release separately using
copied archives/config/extensions. Compare protected bytes and compatibility
before deliberate adoption; never roll back observations or force an old reader
to accept an unsupported schema. Retest affected extension sources/dependencies;
do not copy Ready flags. Test actual approved old/new environments before calling
upgrade/rollback qualified. This guide alone does not complete Stage 5.

Rights/licensing, independent researcher acceptance and explicit maintainer
release approval remain gates. Physical geometry, photometry, precision, photon/
input/audio timing and protocol validity remain each laboratory's responsibility.
They are not universal prerequisites for a scoped stable software distribution.
