# PsyCoLab experiment modularity review

**Reviewed:** 26 October 2026, source baseline `fe888552622a3864f7879497995399e0926d8868`.
**Scope:** official experiment definitions in `src/psychophysics_lab/experiments/`;
historical snapshots are intentionally outside normal menus.

## Decision

Preserve **one stimulus library, one researcher-readable experiment file per
scientific study, one trial runner and one canonical saved-data schema**.

Move only *method-agnostic* trial-strength scheduling/state behind
`psychophysics_lab.methods.contrast`. Keep per-study conditions, timelines,
target alternatives, stimulus composition, contrast interpretation, local
digital headroom, response meaning and primary estimators in the experiment.
Prefer small explicit callbacks over a large autogenerated configuration
framework or a second scene/runner abstraction.

## Confirmed current code patterns

All active study files use recognisable sections:
settings/stimuli, conditions/order, prepare stimuli, one-trial timeline,
response/update, run/finish, and framework declaration.

Several studies already use the same orchestration outline:
`conditions = make_conditions(...)`; initialise; choose; prepare;
`with run.trial(...)`; interpret; update; finish.

### Reuse opportunities, ordered by value

1. **Method selection and state (high):** Generic strategy factories,
   `next_trial`, `trial_record`, `accept_response`, `complete`,
   common trial loop. This is the scope of draft PR #135. Its adaptive
   wrapper calls the experiment's *existing tested* staircase callbacks.
   Shared constant-stimuli scheduling preserves seeded balancing.
2. **Condition identity versus independent staircases (high):** Four
   probe/ellipse studies build scientific conditions and then repeat each
   as separate staircases. For constant stimuli, preserve the unique
   positions/ratios/ring combinations, not the staircase replicas.
   Plan schedule from unique named conditions × strengths × repetitions;
   do not modify their `make_trial` structure.
3. **Strength definitions (high):** Introduce a per-study *declaration*
   of which quantity is controlled, digital units, background and
   contrast-to-intensity mapping. The framework must not assume a
   universal intensity equation. CSF uses digital peak-to-peak grating
   modulation; DetectionScene uses probe increments; orientation
   Gabor uses digital contrast; teaching white-line tasks use absolute
   digital intensity relative to their fixed grey backgrounds.
4. **TUI/Review contract (high):** Prefer method-provided active fields,
   counts and data semantics rather than CSF-specific `if spec.id`
   paths. A shared trial ceiling must be visible in both methods.
   Switching methods must not validate irrelevant hidden fields as
   though active.
5. **Experiment-source examples (medium):** `example_experiment.py`
   should remain beginner-friendly. Supply a tiny local/custom
   experiment example that connects a method with only the experiment's
   scientific declarations and no copied scheduler.
6. **Reusable correctness / response labels (low):** Repeated 2AFC
   correctness checks and key guidance can be small named helpers, but
   keep them explicit where interval/response semantics differ.
   **Do not** merge genuinely different 2IFC and spatial 2AFC
   scientific procedures merely because they look similar.
7. **Common parameter validation helpers (medium):** Parse finite lists
   and bounded numeric levels once; retain stimulus- and geometry-
   specific compositing and Nyquist checks. Invalid values must
   produce recoverable field-level errors before human acquisition.
8. **Separate analysis (high):** Adaptive studies retain existing
   reversal-based estimators and quality flags; fixed-level studies
   produce per-level counts/accuracy and may later use a separately
   qualified psychometric estimator. Never fabricate staircase
   output for a fixed run.

## Changes NOT recommended

- No autogenerated experiment files or reflection-based scientific logic.
- Do not move grating/line/ellipse equations out of the single stimulus
  library or change their default parameters.
- Do not replace validated `adaptive/staircase.py` with a new general
  adaptive engine; the shared interface should delegate to it.
- Do not replace the existing `RunContext`, `TrialTimeline`,
  configuration snapshots or schema-v1 `trials.tsv`.
- Do not force identical threshold estimators or equal contrast units
  across experiments.
- Do not redesign the entire TUI as part of method selection.
- No changes to real participant files, physical calibration or extension
  readiness as part of software architecture improvements.

## Acceptance milestones

**PR #135 — shared method interface and CSF migration.** Review source,
new tests, full CI, synthetic byte-identity for adaptive and fixed CSF
and initial method switching on native Windows. Do not auto-merge.

**Issue #136 — universal adoption.** Add correct method declarations and
selection to each official study (and a clean authoring example) in
small PRs by compatible family: DetectionScene probe/ellipse, teaching
Gabor, teaching line. A method must not appear selectable until its
scientific range and execution are validated.

**Issue #82 — release gates.** Keep installer reproducibility and physical
qualification separate from code-structure approval.

## Status

A reusable API is not equivalent to completed integration across every
experiment. The target is **universally accessible and scientifically
correct methods**, not a universal switch with incompatible behaviour.
